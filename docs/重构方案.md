# AegisCode 重构整合方案

> 本方案基于对 AegisCode v0.2.14（原仓库）与 ApeAdmin v0.2.0（底座）的源码分析，规划新项目的重构路线。三大优化方向的业界参考详见调研仓库报告。

## 一、现状分析

### AegisCode 原架构（重构对象）

```
Web/Electron → FastAPI API → Agent Worker → Model Gateway
                            ↘ Tool Registry → Cloud Workspace / Device ToolJob
背景任务 + Redis Streams 事件 + MySQL/SQLite
```

核心模块（backend/app/services，共 45 个服务，2.4 万行）：

| 模块 | 行数 | 职责 | 重构判断 |
|---|---|---|---|
| tools.py | 1770 | 工具执行器（文件/命令/PPT/DOCX/Excel/浏览器/代码图） | **拆分**：单文件过大，按工具域拆包 |
| model_gateway.py | 672 | 模型配置、自动路由、脱敏、流式 | **保留改造**：对接 ApeAdmin 的 ai_provider 体系 |
| tool_registry.py | 659 | 工具注册 + MCP 三协议发现/调用 | **合并**：与 ApeAdmin MCP-SSE 网关统一 |
| agent_workflow.py | 551 | 四角色 DAG（Planner/Coder/Reviewer/Tester） | **保留改造**：角色协议保留，调度简化 |
| agent_budget.py | 225 | 25轮分段扩展 + 五维预算 | **重点重构**：token 计量精度问题 |
| agent_execution.py | 255 | 运行状态机 + 有界检查点 | **保留**：状态机设计合理 |
| context_policy.py | 205 | token 估算（chars//3）+ 上下文压缩 | **重点重构**：估算粗糙，参考 OpenCode 精确计量 |
| rag_service.py | 639 | ChromaDB + TF-IDF 降级 | 后置：MVP 不迁移 |
| sandbox.py + sandbox_process | 951 | 路径/命令/资源约束 | **保留**：安全边界必须保留 |

### 现存三大问题（重构主攻方向）

**1. 长任务**
- 上下文膨胀：`CHECKPOINT_MAX_MESSAGES=50 / MAX_TOTAL_CHARS=200000` 硬上限，长任务信息丢失
- 分段扩展机制（25→50→75轮）依赖"分段内成功工具数"，进展判定单一，易误判 no_progress 中断
- 恢复链路：中断对账（agent_continuity 143行）与检查点耦合，恢复后上下文重建不完整

**2. Token 消耗统计**
- `estimate_tokens = chars // 3`：中英混合粗估，误差大，预算控制失真
- UsageLog 仅记录 prompt/completion/total/cost 四字段，**缺维度**：无 tool_calls、cache_hit、reasoning（思维链）、分段/角色维度
- 无实时预算反馈：预算耗尽才终止，跑超了无法提前预警
- cost 用 String(20) 存 Decimal，精度隐患

**3. Agent 运转机制**
- 调度复杂：agent_dispatch + executor_lease + admission 三层，本地单机部署下过度设计
- 可观测性弱：运行事件靠 Redis Streams，无结构化 trace（无 span/step 耗时分解）
- 循环保护：repeated_tool_result 检测只有简单指纹，误杀率高

## 二、新架构：ApeAdmin 插件化底座

```
┌─────────────────────────────────────────────┐
│ ApeAdmin 底座（继承）                         │
│ RBAC / 安装向导 / 插件市场 / 审计 / MCP-SSE  │
├─────────────────────────────────────────────┤
│ aegis_agent 插件（核心重构）                  │
│  ├─ agent_runtime   状态机+检查点+恢复        │
│  ├─ agent_budget    精确 token 计量+预算      │
│  ├─ agent_workflow  多角色 DAG                │
│  ├─ model_gateway   模型路由（复用底座 ai）    │
│  ├─ tools/          工具包（按域拆分）        │
│  └─ usage           用量统计（多维）          │
├─────────────────────────────────────────────┤
│ aegis_workspace 插件（项目与工作区）           │
│  ├─ projects        项目/成员/文件            │
│  ├─ sandbox         沙箱执行                  │
│  └─ git             快照与审阅                │
└─────────────────────────────────────────────┘
```

### 设计原则

1. **插件边界**：Agent 能力拆为两个插件，`aegis_agent`（运行时）与 `aegis_workspace`（工作区），互不依赖也可独立运行，通过 EventBus 通信
2. **复用底座**：用户/角色/菜单/审计走底座 RBAC；模型管理对接底座 `ai_provider` API；MCP 工具统一走底座网关注册
3. **数据模型**：表名前缀 `aegis_agent_*` / `aegis_workspace_*`，迁移走底座 alembic 链
4. **前端**：Vue 页面放 `frontend/src/views/{plugin}/`，复用底座布局与权限指令

## 三、三大问题重构方案

### 3.1 长任务稳定性

| 原实现 | 新方案 | 参考 |
|---|---|---|
| 25轮分段硬扩展 | 任务分解优先：Planner 先产 subtask DAG，每子任务独立上下文窗口 | OpenHands 的 task decomposition |
| 检查点截断 | 分层上下文：system + 摘要层（旧轮压缩摘要）+ 工作层（近 N 轮原文）+ 检索层（RAG 按需） | Cline/Roo 的 summarization |
| no_progress 单指标 | 进展多信号：diff 有变化 / 验证通过 / 新文件 / 用户确认，加权判定 | Aider 的 git-diff 反馈 |
| 恢复重建不完整 | 检查点包含完整工具结果摘要 + 文件状态指纹，恢复时重建工作区快照 | OpenHands 恢复机制 |

### 3.2 Token 精确统计

新 `usage` 设计（对标 OpenCode /usage 与 Gemini CLI 的统计深度）：

```python
class AegisUsageLog:          # 每次模型调用一条
    run_id / step_id          # 关联 Agent 运行与步骤
    role                      # planner/coder/reviewer/tester 角色维度
    model / provider
    input_tokens / output_tokens      # API 返回的精确值（usage 字段）
    cache_read / cache_write          # 缓存命中维度（DeepSeek/OpenAI 兼容）
    reasoning_tokens                  # 思维链维度
    context_tokens                    # 本次请求上下文规模
    cost_usd (Decimal)                # 精确成本，改用 DECIMAL(12,6)
    latency_ms / first_token_ms       # 延迟维度
    budget_snapshot                   # 记录时预算余量（实时反馈数据源）
```

配套：
- 预算控制器改为**流式实时扣减**：每 SSE chunk 回调时累计，接近阈值（80%）向前端推送预警事件
- token 估算仅用于显示预估，预算控制一律以 API usage 返回值为准（cache 字段区分）
- 用量看板按 run/role/model/用户 四维聚合，支持导出

### 3.3 Agent 运转机制

| 原实现 | 新方案 |
|---|---|
| dispatch+lease+admission 三层 | 单机模式内联执行 + 预留 Worker 接口（先用 SQLite 队列，规模到了再拆进程） |
| Redis Streams 事件 | 底座 EventBus（进程内）+ SSE 直推前端；事件结构化落库 `aegis_agent_events` |
| 无 trace | OpenTelemetry 语义的 span：每 run/step/tool_call 三级，含耗时/token/结果码 |
| 循环简单指纹 | 工具调用序列窗口（近10次）+ 参数相似度 + 结果哈希三重检测，先警告后终止 |
| write_scope 声明 | 保留角色协议 + scope 校验，冲突 coder 串行（原实现合理，保留） |

## 四、分期路线

### Phase 1 — 底座跑通 + Agent 最小内核（MVP）
- [ ] 底座启动：安装向导、RBAC、菜单（复用验证）
- [ ] `aegis_agent` 插件骨架：插件注册、AgentRun/Step 模型、基础对话循环（单角色）
- [ ] 模型对接：复用底座 ai_provider，支持 DeepSeek/OpenAI 兼容端点
- [ ] 精确 usage 记录（3.2 数据模型先行，为后续优化积累数据）

### Phase 2 — 工具体系 + 工作区
- [ ] `aegis_workspace` 插件：项目管理、文件树、上传
- [ ] tools 拆包重构：file / command / search / document 四域
- [ ] 沙箱约束迁移（路径/命令/资源）
- [ ] Git 快照与审阅

### Phase 3 — 长任务 + 多 Agent
- [ ] 分层上下文与摘要压缩（3.1）
- [ ] 检查点/恢复/暂停续跑
- [ ] Planner DAG + 四角色工作流
- [ ] 三重循环检测

### Phase 4 — 观测与运营
- [ ] span 三级 trace + 事件落库
- [ ] 用量看板四维聚合 + 预算实时预警
- [ ] MCP 工具市场打通（底座网关）
- [ ] 后置：RAG、Electron 端、企业治理（OIDC/审批）

## 五、迁移与丢弃清单

**迁移**（重写适配插件体系）：agent_execution 状态机、sandbox 约束、model_gateway 路由、git_snapshot、tool_registry 的 MCP 发现
**重写**：agent_budget（精确计量）、context_policy（分层上下文）、usage（多维模型）、tools（拆包）
**暂不迁移**：rag_service（后置）、enterprise_*（后置）、redis_service（用 EventBus 替代）、electron（后置）、vision_proxy/multimodal（后置）、Aider 风格的 PPT/DOCX/Excel 生成工具（非核心，后置）
